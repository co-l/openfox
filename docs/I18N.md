# OpenFox Internationalization (en + fr)

OpenFox ships with two UI languages — English and French — via a hand-rolled
`t()` system. There is no i18next/lingui dependency; the whole thing is a small
typed helper over a `Translation` object.

## Architecture

| Layer       | Helper                                                                     | Locale source                                                |
| ----------- | -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Shared core | `t(tx, vars?)` in `src/shared/i18n/index.ts`                               | module-level `currentLocale`                                 |
| Web UI      | `useT()` hook + `t` in `web/src/stores/locale.ts`, `web/src/hooks/useT.ts` | server `/api/config` → `navigator.language` when `automatic` |
| Server      | `serverT(tx, vars?)` in `src/server/i18n.ts`                               | DB `display.locale` setting                                  |
| CLI         | `cliT(tx, vars?)` in `src/cli/i18n.ts`                                     | DB `display.locale` setting (read-only)                      |

### Translation objects

```ts
type Translation = { en: string | Plural; fr: string | Plural }
type Plural = { one: string; other: string }
```

Both locales are mandatory at the type level — there is deliberately **no
fallback**: a missing `fr` entry is a compile error, never a runtime gap.

- String entries are interpolated via `{{name}}` placeholders. Unknown
  placeholders are left untouched so a missing variable can never silently hide
  a broken translation.
- Plural entries pick the category via `Intl.PluralRules` for the active locale,
  using `vars.count`.

### Locale resolution

- The setting key is `display.locale` (DB-backed, default `automatic`).
- **Web:** the server delivers the active locale via `/api/config`; the client
  resolves `automatic` to `navigator.language` clamped to `en`/`fr`.
- **Server + CLI:** `automatic` resolves to `en` — the server/CLI cannot know
  the browser language, so only users who explicitly pick a language see
  translated server/CLI output.

The `Language` setting lives in **Settings → Display** and persists to the DB.

## Rules

- English strings in code stay **byte-identical** to the original English
  string — existing tests assert them.
- Server-side message consts may be grouped near usage or in
  `src/server/i18n.ts`.
- Keep translations user-facing only — see the non-goals below.

## Deliberate non-goals

The following content is **not** translated and stays English:

- **LLM-facing content** — system prompts, system reminders, task-board
  reminders/audit entries, dynamic-context notices, agent definitions. The
  model is instructed separately about the user's language; translating these
  would be noise.
- **External tool output** — git output, shell output, dev-server logs, MCP
  server messages, npm/journalctl output. These come from third-party tools in
  whatever language they produce.
- **Dev-facing / debug strings** — `logger.*` messages, internal exception
  messages, deprecated-protocol notices pointing at docs.
- **Test fixtures, docs, `.openfox/`** — test data and documentation are not
  user-facing runtime strings.

## Tests

- `src/shared/i18n/index.test.ts` — core `t()`/`interpolate`/plural/locale
  behavior, including a compile-time proof that a `Translation` missing `fr`
  fails to typecheck.
- `src/server/i18n.test.ts` — `serverT()` DB-driven resolution.
- `src/cli/i18n.test.ts` — `cliT()` DB-driven resolution + fallback.
- Web: `web/src/stores/locale.test.ts` — store resolution of `automatic` →
  `navigator.language` and re-render on locale change.
